# IntelliFind

**An AI-native automated-procurement platform for repair shops and suppliers — investor demo simulation.**

IntelliFind sits between **repair shops** (the retailers/customers) and **suppliers**, and
automates procurement: it continuously watches each shop's inventory and demand, scores every
supplier offer on a **risk-adjusted economic basis**, routes market & limit orders, brokers
peer-to-peer inventory swaps between shops, and tracks the long-term P&L consequences.

This repository contains the **first version**: a fully interactive, real-time **simulation +
live dashboard** used to demonstrate the product concept to investors. It contains **no AI /
ML yet** — demand is generated by predefined stochastic processes, and procurement weights are
configurable. The architecture is deliberately modular so an **AI optimisation layer** can be
added later without rebuilding anything (see [Future AI](#future-ai)).

---

## Quick start

No dependencies — the whole thing runs on the **Python 3 standard library**.

```bash
python3 -m sim.server            # then open http://localhost:8000
python3 -m sim.server --port 8080 --autostart
```

Open the dashboard, press **▶ Start**, and watch inventory, demand, prices, orders, defaults,
trades and P&L evolve in real time. Use the **Controls** tab to change the scenario (seed,
volatility, spike frequency, delivery times, prices, weights, …) and **Apply & Reset**.

Run the tests:

```bash
python3 -m unittest discover -s tests        # 31 tests, stdlib only
# or, if you have pytest:  python3 -m pytest tests
```

Run a headless strategy sweep from the command line:

```bash
python3 -m calibration.sweep
```

## What you can watch (the demo story)

The single most important thing the simulation makes visually obvious (spec §36):

> **Traditional procurement:** "Supplier B is cheapest, so buy from Supplier B."
>
> **IntelliFind:** "Supplier B is cheapest, but it defaults often and delivers slowly.
> Supplier C costs a little more but is far more reliable and faster. Once every economic
> factor is priced in, Supplier C has the lower total procurement score." — and that decision
> flows through to **fewer stockouts → higher customer satisfaction → higher long-term P&L.**

The **Procurement Engine** tab shows, for every real decision, each supplier's price, risk,
delivery and bulk-quantity mismatch, the four normalised component scores, the weights, and the
final score — with the selected supplier highlighted. The **Strategy Lab** runs many weight
configurations headlessly and ranks them by long-term P&L, showing that risk/delivery-aware
strategies beat naive "cheapest wins" procurement (typically hundreds fewer stockouts and
higher P&L).

## Architecture

```
engine/                       Pure simulation engine (no I/O)
├── config.py                 SimulationConfig — every tunable parameter
├── rng.py                    Seeded, reproducible, independent random streams
├── entities.py               Repair-shop / supplier / market-product state
├── demand_engine.py          Baseline + noise + occasional spikes; churn feedback
├── inventory_engine.py       Thresholds, days-of-cover, status, consumption
├── supplier_engine.py        Pricing (market index + stock + noise), risk / defaults, restock
├── procurement_engine.py     Score calculator, market orders, limit orders, 60:40 scatter
├── intra_retail_engine.py    Complementary swap detection + exchange-rate execution
├── financial_engine.py       Revenue, costs, customer satisfaction, P&L
├── order_book.py             Market / limit / intra-retail order lifecycle
├── events.py                 Structured event log (ML-ready records)
└── simulation.py             Tick-loop orchestrator + snapshot + score↔P&L tracking

calibration/sweep.py          Headless strategy sweep (parameter set → long-term P&L)
sim/server.py                 Stdlib HTTP server + REST API (runs the sim in a thread)
sim/static/                   Dependency-free dashboard (index.html, app.js, style.css)
tests/                        unittest suite (engine + intra-retail)
mcp_server/, agent/           Placeholders for the future AI layer (see below)
```

### Key conventions

* **Time** is in *ticks*; `ticks_per_day` (default 24 → 1 tick = 1 hour) ticks make a day.
* **Procurement score is a cost: lower = better**, used consistently everywhere.
* **Randomness is fully reproducible** from a single `seed`; the same seed reproduces the
  identical scenario (spec §25).

### Procurement score

```
Score = W_price·PriceScore + W_risk·RiskScore + W_delivery·DeliveryScore + W_quantity·QtyMismatchScore
        (weights sum to 1;  each component normalised to [0,1] against stable reference scales)
```

Absolute (not per-tick) normalisation is used so a score is comparable across suppliers, over
time and between strategies — which is what makes the score-over-time chart and the empirical
score↔P&L relationship meaningful.

## Data logging

Every meaningful event (`market_order`, `supplier_default`, `stockout`, `intra_retail_trade`,
`limit_order_executed`, `supplier_delivery`, `pnl_update`, …) is written as a flat,
JSON-serialisable record. Download the full log from **Controls → Export event log**, or
`GET /api/export`. This is the raw material the future ML layer will train on.

## <a name="future-ai"></a>Future AI (not implemented yet)

The current version deliberately contains **no AI**. The design supports adding it cleanly:

```
Historical simulation data  →  AI agent  →  procurement-parameter optimisation
        →  procurement engine  →  simulation  →  P&L feedback  ↺
```

* `calibration/sweep.py` already produces the `(parameter set → long-term P&L)` signal a learner
  needs — the **Strategy Lab** is a brute-force stand-in for the optimiser.
* `agent/` will hold the optimisation agent; `mcp_server/` will expose the engine to it as tools.
* Demand spikes are generated (not predicted) today; a forecasting agent will later try to
  predict them and pre-position inventory.
